# خطة الخطوة التالية: محرك محادثة قابل للتوسع

## الحالة الحالية

يضم المشروع وحدات Gradle `:app` و`:core` و`:storage`. وحدة التخزين مؤسّسة للتحقق من توافق البناء فقط؛ لا تحتوي بعد على قاعدة أو حفظ فعلي. لا تزال `MainActivity.kt` واجهة تجريبية: الرسائل وحالة الإرسال تعيشان في Compose، ولا يوجد ربط فعلي بمحرك أو مزوّد ذكاء اصطناعي أو تخزين محلي.

أُنجزت المرحلة الأولى في `core` بوصفها نماذج وعقود فقط، دون تنفيذ تخزين أو اتصال شبكي:

- نماذج `Conversation` و`Message` و`MessageContent` ومعرّفات ذات أنواع مخصصة، وأدوار وحالات وانتقالات وأخطاء صريحة.
- نماذج موحدة لطلبات المزوّدين ونتائجهم، وواجهات `AIProvider` و`ProviderResolver` و`ConversationRepository` و`ConversationEngine`.
- نماذج وواجهة تنسيق عامة لطلبات الأدوات ونتائجها والموافقات، مع بصمة طلب مرتبطة بالمحادثة والاستدعاء، وحالات للتعافي وحدود تنفيذ مقترحة. لا يوجد تنفيذ MCP أو نظام صلاحيات.
- اختبارات وحدات مصدرية في `core/src/test` تغطي النماذج والعقود وحالات الموافقة والتزامن والتعافي. المستودع المستخدم في اختبارات العقد fixture داخل الذاكرة، وليس Room.

اكتملت المرحلة A عند Commit `c36503e`؛ نجحت اختبارات `:core:test` وعددها 33 اختباراً (33/33)، كما نجح بناء Debug APK في GitHub Actions. أُسست وحدة `:storage` في المرحلة B، لكن توافق Room/KSP لم يُثبت بعد. ينتظر ذلك نجاح Workflow بهذه التغييرات، بما في ذلك تنفيذ فحصي KSP المستقلين لـDebug وRelease وبناء المكتبة في الوضعين.

إعداد Gradle يضم `:core` و`:storage` ويستخدم Kotlin JVM `2.4.21` وCompose plugin `2.4.21` وAGP `9.3.1`. وحدة `core` تستهدف JVM 17، وتضع `kotlin-test` و`kotlinx-coroutines-test` ضمن اعتماديات الاختبار فقط. تبعيات Room/KSP محصورة في `:storage` ولا توجد في `core`.

Workflow في `.github/workflows/android-debug.yml` يهيئ Temurin JDK 17 وGradle 9.5.0 على GitHub، ثم يشغّل `:core:test`، ويتحقق من اعتماديات `:storage`، وينفّذ `:storage:kspDebugKotlin` و`:storage:kspReleaseKotlin` مع سجل وفحص مستقل لكل منهما، ثم يبني `:storage:assembleDebug` و`:storage:assembleRelease` قبل `:app:assembleDebug`. لم تُتحقق نتيجة Workflow بهذه التغييرات بعد.

## الشكل المستهدف

اعتماد نموذج مجال واحد مستقل عن Compose وعن واجهات الشبكة:

- `Conversation`: معرّف ثابت، عنوان، أوقات الإنشاء والتحديث، المزوّد/النموذج المختار، وحالة الأرشفة عند الحاجة.
- `Message`: معرّف، `conversationId`، دور (`system`, `user`, `assistant`, `tool`)، محتوى منظم، وقت الإنشاء، حالة الإرسال، وبيانات المزوّد الاختيارية.
- `MessageContent`: نص الآن، مع قابلية إضافة أجزاء/مرفقات لاحقاً دون تغيير معنى النص الحالي.
- الحالات والأخطاء تكون أنواعاً صريحة؛ لا تمثل رسالة فاشلة كسلسلة نصية عادية.

واجهة المزوّد تكون عقداً في طبقة مستقلة، مثلاً `AIProvider`، تستقبل طلباً موحداً (الرسائل، النموذج، الخيارات والإلغاء) وتعيد أحداثاً/نتيجة موحدة. يعرّف العقد أيضاً معرّف المزوّد وقدراته، ويحوّل كل Adapter صيغة المزوّد إلى هذا النموذج. لا تضع مفاتيح أو تفاصيل HTTP في طبقة المجال أو الواجهة.

`ConversationEngine` ينسق التدفق: يتحقق من المدخلات، يحفظ رسالة المستخدم، يختار المزوّد، يرسل السياق، يعرض حالة التقدم/الأجزاء المتدفقة، ثم يحفظ الرد أو الخطأ. يعتمد على واجهتي التخزين والمزوّدات، لا على Compose أو Android Views. الواجهة تتعامل مع حالة شاشة ونداءات ViewModel/UseCase فقط.

## خطة التنفيذ المقترحة

### 1. تأسيس المجال والعقود — أُنجز

تأسست وحدة `:core` بالنماذج والعقود الموضحة أعلاه، وأضيفت اختبارات وحدات لها. لا تحتوي الوحدة تطبيقاً لمحرك أو مستودع أو مزوّد فعلي، ولا تعتمد نماذج المجال على Android أو Compose أو Room أو HTTP أو MCP. اعتماد `kotlinx-coroutines-test` خاص بالاختبارات؛ لم تضف اعتماديات تشغيلية للكوروتين إلى `core`.

**حالة القبول:** اكتملت المرحلة A. نجح `:core:test` بعدد 33/33 وبناء Debug APK في Workflow المرتبط بـ `c36503e`.

### 2. التخزين المحلي

أُسست وحدة `:storage` وأُضيف تحقق CI لحل الاعتماديات وتشغيل KSP فعلياً لكل من Debug وRelease وتجميع المكتبة في الوضعين؛ هذه هي بنية المرحلة B فقط. لم يُشغّل Workflow بهذه التغييرات بعد، لذا لا يُعد توافق Room/KSP مثبتاً ولا تُعد المرحلة B مقبولة تنفيذياً حتى تنجح فحوص KSP المستقلة ويكتمل `:storage:assembleDebug` و`:storage:assembleRelease`. بعد ذلك يمكن بدء تنفيذ عقد `ConversationRepository` باستخدام Room ضمن المرحلة التالية، مع معاملات ذرية واختبارات وmigrations وسياسة حذف وأرشفة. لا تحفظ مفاتيح المزوّد في قاعدة المحادثات.

**اعتماديات Gradle:** Room runtime/compiler مع KSP، واختبار قاعدة بيانات محلية. ينبغي حسم سياسة الاحتفاظ بالمحادثات والنسخ الاحتياطي قبل تفعيل مزامنة أو تصدير.

### 3. محرك المحادثة وربطه بالواجهة

تنفيذ `ConversationEngine` في `core` مع مستودع ومزوّدين وهميين للاختبار أولاً. اجعل اختيار المزوّد صريحاً، ومرر سجل المحادثة بترتيبه، وادعم الإلغاء وحالات `sending/streaming/completed/failed/cancelled/interrupted`. بعد ثبوت عقود التخزين والمحرك، انقل حالة الشاشة ومنطق الإرسال من `MainActivity` إلى ViewModel/StateFlow. عالج إنشاء محادثة جديدة واستعادتها وتحديث العنوان.

**اعتماديات Gradle:** Lifecycle ViewModel Compose عند إدخال ViewModel؛ coroutines وواجهات مستودع قابلة للاستبدال. اختبر المحرك بمزوّد وهمي ومستودع داخل الذاكرة دون شبكة.

### 4. طبقة المزوّدات ثم Gemini وCodex

إنشاء `providers` وتنفيذ Registry يربط معرّف المزوّد بالـ Adapter. أضف Gemini عبر واجهة Google الرسمية المعتمدة وقت التنفيذ، مع DTO منفصلة، تحويل الأخطاء/حدود الاستخدام، وخيار بث إن كان مدعوماً. بالنسبة إلى Codex، حدّد أولاً الواجهة المدعومة رسمياً وسياق المصادقة المسموح للتطبيق؛ لا تفترض أن واجهة منتج Codex أو جلسة المستخدم هي API عامة قابلة لإعادة الاستخدام. لا تبدأ Adapter قبل حسم ذلك. يمكن إضافة مزوّدات لاحقة بتنفيذ العقد نفسه دون تعديل المحرك.

**اعتماديات Gradle:** اختر SDK رسمي أو عميل HTTP موثقاً لكل Adapter بعد مراجعة التوافق والترخيص والحجم. لا تضف تبعيات SDK عشوائية إلى `app`. أضف `INTERNET` في Manifest عند بدء الاتصال الفعلي. خزّن الأسرار باستخدام آلية آمنة مناسبة مثل Android Keystore، ولا تضع مفاتيح ضمن المصدر أو السجلات؛ وضّح أن مفتاحاً مضمناً في تطبيق عميل لا يمكن حمايته بالكامل من مستخدم الجهاز، وقد يلزم خادم وسيط لإدارة الأسرار والحصص.

### 5. إكمال التكامل وضبط الاعتمادية

أضف معالجة المهلات والانقطاع وHTTP errors وحدود الحصة، وإيقاف البث عند مغادرة المحادثة، وحدود طول السياق، ورسائل خطأ مفهومة. أظهر المزوّد والنموذج والتكلفة/الحصة عند توفر بيانات موثوقة. أضف اختبارات للتحويلات والعقود، واختبار تكامل اختياري باستخدام بيئة أسرار محلية غير ملتزمة بالمستودع. راجع سياسة Android backup للبيانات الحساسة.

## تغييرات Gradle المتوقعة

وحدتا `:core` و`:storage` مضافتان بالفعل إلى `settings.gradle.kts`؛ `:storage` يحتوي إعدادات Room/KSP فقط، دون نماذج تخزين أو تنفيذ. تبقى `:providers` ووحدات MCP والصلاحيات غير مضافة. راجع إصدارات الاعتماديات وشغّل CI عند كل إضافة. إعداد Compose لا يوفر وحده بنية المجال أو التخزين أو الاتصال.

## المخاطر والقرارات المفتوحة

- **Codex والمصادقة:** قد لا تكون واجهة Codex المطلوبة متاحة كت API عامة لتطبيق Android؛ هذا قرار مانع قبل تقدير/تنفيذ Adapter.
- **الأسرار والحصص:** المفتاح الموجود على الجهاز قابل للاستخراج بدرجات متفاوتة؛ خادم وسيط يزيد كلفة التشغيل والمسؤولية، بينما BYOK يتطلب شرحاً واضحاً وتأمين تخزينه.
- **البث والحفظ:** حفظ أجزاء الرد تدريجياً يحافظ على العمل عند الانقطاع لكنه يزيد تعقيد حالات الرسالة والكتابة المتزامنة. ابدأ برسالة قيد الإنشاء وتحديثات مضبوطة.
- **تطور المخطط:** أنواع المحتوى والمرفقات والرسائل المنفذة عبر الأدوات تحتاج migrations وتوافقاً خلفياً. ابدأ بنموذج نصي واضح ولا تخلط نتائج الأدوات برسائل المستخدم.
- **خصوصية البيانات:** Room تخزين محلي وليس تشفيراً تلقائياً. يلزم تحديد أثر النسخ الاحتياطي، الحذف، وتسجيل البيانات قبل حفظ محتوى حساس.
- **التوافق والحجم:** SDKs قد ترفع حجم APK أو تتطلب إعدادات/إصدارات Kotlin إضافية. تحقق من توافقها مع AGP وCI قبل اعتمادها.
- **حدود السياق والتكلفة:** لكل مزوّد حدود وأسعار وسلوك مختلف؛ طبقة القدرات والإعدادات يجب أن تمنع عرض وعود موحدة غير دقيقة.

## ترتيب الإنجاز ومعيار القبول

الخطوة التالية هي تشغيل GitHub Actions والتحقق من تقارير `:core:test` و`:storage` و`:app:assembleDebug`. لا تُقبل المرحلة B حتى يبيّن السجلان المستقلان تنفيذ `:storage:kspDebugKotlin` و`:storage:kspReleaseKotlin` دون تخطٍّ، وينجح تجميع `:storage:assembleDebug` و`:storage:assembleRelease`. لا تبدأ إنشاء المخطط أو كيانات Room أو DAOs قبل نجاح هذه الشروط ومراجعة النتائج.

تعتبر الخطوة الأساسية مكتملة حين يمكن إنشاء محادثة، إرسال رسالة، استقبال رد عبر عقد المزوّد، رؤية الحالات والأخطاء، ثم إغلاق التطبيق وإعادة فتحه مع بقاء المحادثة، وكل ذلك دون أن تعتمد طبقة المحرك على Compose أو تفاصيل مزوّد بعينه.
